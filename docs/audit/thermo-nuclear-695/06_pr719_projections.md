## 1. The new test's `GOLDEN` is a second registry, and the file says it prevents one

`tests/test_setup_projection.py:30-32` states the design intent: "A golden per host is what keeps a second registry from appearing: only the profile moves when a host's setup surface changes." The `GOLDEN` dict at `:33-64` is a hand-typed, field-for-field copy of the six `profiles/<host>.json#setup` blocks (`profiles/grok.json:7-13`, `codex.json:7-13`, `antigravity.json:7-13`, `droid.json:7-13`, `omp.json:7-13`, `opencode.json:7-13`). `test_golden_setup_projection_per_builtin_host` (`:67-71`) then asserts `asdict(resolve_setup_projection(host)) == GOLDEN[host]`.

That is not generated by the code under test, and it is not an independent expectation either: it is a mirror of the input file, so the assertion can only fire when the two hand-maintained copies drift. It cannot catch a wrong-but-consistent declaration — if `codex` should really have been `host-cli`, both copies would say `host-catalog` and the test stays green. The price is concrete: from now on every profile setup change must touch the profile **and** this test, and the comment asserts the opposite of the mechanism.

Remedy (keeps all observable behaviour, deletes the duplicate data): replace `GOLDEN` with invariants that are genuinely independent of the profile's own literals —
- `source == "host-catalog"` ⇒ `catalog` is repo-relative, the file exists, and the two existing catalogs are *different* (`.codex-plugin/models.json` binds `gpt-6.1-sol` / `gpt-6-luna`; `.antigravity-plugin/models.json` binds `pro` / `flash` / `flash_lite`) — an independent fact about the tree;
- `source == "inherit"` ⇒ the same profile's `runtime_conventions.default_model == "inherit"` and `"model"` is in `forbidden_spawn_fields` (`profiles/droid.json:86-95`) — cross-field consistency, not a copy;
- `source == "host-cli"` ⇒ `skills/<skill>/SKILL.md` exists (the resolver already enforces this at `scripts/setup_pstack.py:53-57`);
- `source == "none"` ⇒ no catalog artifact is shipped for that host.
Plus one explicit Grok expectation if the author wants the exact values pinned. Net obligation removed: six duplicated blocks and the "edit two files" duty.

## 2. `test_every_builtin_profile_setup_block_is_typed` compares the profile to a copy of itself

`tests/test_setup_projection.py:291-299` reads `profiles/<host>.json`, builds `SetupProjection(**data["setup"])`, validates, and asserts `asdict(projection) == GOLDEN[host]`. It never calls `resolve_setup_projection` — the code the file exists to cover — and its expectation is `GOLDEN`, i.e. the same literals it just read. This is the strictest form of tautology in the file: profile == copy-of-profile.

Coverage it appears to add is already held by `tests/test_portability_schemas.py:256-272`, which passes `setup=data.get("setup")` into a real `HarnessProfile` and asserts `isinstance(profile.setup, SetupProjection)` for every profile in `profiles/`. Delete `:291-299`, or fold its artifact invariants into finding 1.

## 3. Candidate contract in the test contradicts the profile in the same PR

`tests/test_setup_projection.py:91-94` is named `test_candidate_profiles_declare_no_setup_surface`, with the docstring "A candidate host cannot point at a setup surface it has no evidence for", over hosts `("claude", "copilot")`. But `profiles/droid.json:3` is `"support_state": "candidate"` and `:7-13` declares `{"source": "inherit", "effort": "inherit-parent"}`. Droid is the only *built-in* candidate (`scripts/host_identity.py:27`), and the test omits it; the two hosts it does cover are a legacy alias (`claude`, `host_identity.py:33`) and an identity that is not in `KNOWN_HOSTS` at all, resolving only because `profiles/copilot.json` exists.

The file therefore encodes two contradictory rules: `:93` says candidates declare no setup surface, `:295-298` iterates `BUILTIN_HOSTS` (which includes candidate `droid`) and requires `data["setup"]` to exist. The normative sources side with droid: the OpenSpec requirement (`openspec/specs/pstack-setup-overlays/spec.md:8-16`) forbids only a candidate declaring a *CLI-probing* surface, and `scripts/setup_pstack.py:44-50` implements exactly that. The test passes only because the host list was hand-picked to avoid the case.

Remedy: rename to the rule that actually holds ("a candidate may declare only a passive surface; a CLI probe is refused"), assert droid's `inherit` positively, and keep the negative control as a tmp-dir fixture (`:201-218` already does the negative half). This also removes the trap where a reader "fixes" droid to satisfy the test name.

## 6. Do the six profiles carry real per-host data?

Mostly yes, and better than the diff shape suggests.
- `grok` (`profiles/grok.json:7-13`, `host-cli`) is the only CLI-probing surface, and it is the only one with a `skill` plus overlay — matches `skills/setup-pstack-grok/SKILL.md:9-15`.
- `codex` and `antigravity` (`:7-13`, `host-catalog`) point at two genuinely different, host-specific catalogs that exist in-repo and bind different model families (GPT-6.x vs Gemini Pro/Flash). Not a string swap.
- `droid` (`:7-13`, `inherit`) agrees with its own `runtime_conventions` (`default_model: "inherit"` at `:86`, `model` in `forbidden_spawn_fields`) — independently corroborated, not copy-paste.

Copy-paste residue, both removable without behaviour change:
- **`effort` is a pure function of `source`.** `scripts/portability_types.py:34-40` maps `host-cli→live-enum`, `host-catalog→none`, `inherit→inherit-parent`, `none→none`, and `validate()` (`:369-374`) rejects any mismatch. So the field carries zero per-host information in all six files, yet it must be typed six times, is enum-constrained twice (`SETUP_EFFORT_MODES` at `:30` and the JSON schema), and needs three dedicated rejection rows (`tests/test_setup_projection.py:137,139,141`). Derive it in `SetupProjection` and delete the field from the profiles, the schema's `required` list, and those rows.
- **Eleven information-free nulls.** `profiles/codex.json:9,11`, `antigravity.json:9,11`, `droid.json:9,10,11`, `omp.json:9,10,11`, `opencode.json:9,10,11` spell out `"skill": null, "catalog": null, "overlay": null`. The schema requires only `source` and `effort` (`schemas/portability/setup-projection.schema.json:6`) and the dataclass already defaults all three to `None` (`portability_types.py:351-362`), so `SetupProjection(**raw)` yields the identical object without them. `asdict` still produces `None`, so `GOLDEN` compares equal either way. Delete them.

Two value judgements I could not fully corroborate from the repo:
- `omp`/`opencode` declare `source: "none"`, documented as "this host exposes no model or effort setup surface" (`setup-projection.schema.json:18`). But both profiles declare `runtime_conventions.default_model` (`profiles/omp.json:270` = `pi`, `opencode.json:248`) and `omp` lists `model` among `allowed_spawn_fields` (`:271-275`) — so the host *does* expose model choice; what is true is that pstack ships no setup for it. The entry skill then turns that into `BLOCKED` (`skills/setup-pstack/SKILL.md:37`). Consider naming the real state (unimplemented) or adding a note, so pstack's gap is not recorded as the host's absence. `MARK UNVERIFIED` for the hosts' own config surfaces: I found no in-repo evidence either way, and I did not consult upstream host docs.
- `codex`'s `host-catalog` row is coherent with the shipped catalog, while `examples/portability/model-role-policy.example.json` marks codex `discovery: "unverified"`. That file is an empty-catalog template (`model_catalog: []`, every tier `inherit-parent`), so I do not treat it as a contradiction — noted only so the author can confirm which document is authoritative for codex discovery.
